A history, built from snapshots.

Git is a distributed version-control system. It records snapshots of a project over time and connects them into a history. A normal local repository holds its own objects and history: you can commit, branch, compare and recover work without a server or an internet connection.

Git manages the history.
GitHub gives that history a collaborative home.

GitYour files, snapshots, branches and local history.Works completely locally.
⇄optional exchange
HTTPS / SSH
A hosting serviceGitHub, GitLab, Bitbucket, or your own server.Shared repositories + collaboration.

First, make the invisible visible. An edited file, its staged content and its last committed version may all differ. A branch is a name. HEAD is your current position. Commands become easier when those things have a place on the page.

Then, follow the objects. Commits point to trees; trees name blobs. Parent links form a directed acyclic graph. Hashes tie identities to content. This structure explains both everyday workflows and the unsettling moments when history seems to disappear.

Part I · Seeing Git

Four places. Different responsibilities.

“My file is in Git” is too vague. Ask which version of it, in which state, and under which name.

01 · The mental model

The four places you need to see

01

Working tree

The files you can open and edit. They may differ from the last commit and from the staged version.

02

Index / staging

The proposed next snapshot: path names, modes and object IDs, plus bookkeeping and possible conflict entries.

03

Local repository

Objects and names: commits, trees, blobs, refs and reflogs. Your recorded history lives here.

04

Remote repository

Another repository, on a service, server or local path. It has its own refs and objects.

add · working content → index + blob objects
commit · index → tree + commit + ref update
restore · index or chosen tree → selected content
switch · branch snapshot → HEAD, index, working tree
fetch · remote → local objects + tracking refs
push · local objects/ref proposal → remote
reset · target commit → ref; optionally index/files
pull · fetch, then integrate into current branch
These are conceptual layers. The index normally sits inside the repository’s metadata directory. A remote-tracking ref such as origin/main is local information about a remote, not a live connection. Nothing in this diagram means files are physically moved from folder to folder.
02 · A running Linux example

Start with an ordinary directory.

Use a new ~/Documents/git-demo directory for these examples. Later sections branch into independent scenarios starting from this project; they are not one long script to paste blindly. The opening film uses this same three-file project.

cd ~/Documents
mkdir git-demo
cd git-demo
git init -b main
printf '<h1>Hello</h1>\n' > index.html
printf 'body { color: #29312d; }\n' > styles.css
printf '# Git demo\n' > README.md
git status

git init

“Give this directory a repository.” Git creates metadata, an object store and an initial HEAD. -b main explicitly chooses the initial branch name; defaults vary with configuration.

Beforefiles only
→
Afterfiles + .git/

It does not stage files or create a commit. HEAD can name the unborn main branch before main has a commit ID. Re-running init in an existing repository is normally safe.

Common mistake: expecting init to upload files. Related: clone, add, commit.

git clone

“Make a usable local repository from another one.” A normal clone obtains repository objects/history, configures a remote named origin and remote-tracking refs, then checks out an initial branch into a working tree.

cd ~/Documents
git clone https://github.com/USER/PROJECT.git

This is more than a ZIP download. --depth, --filter, --bare and other options change what is created or transferred. Cloning a local path need not use a network.

Part II · Everyday Git

Build a deliberate snapshot.

Inspect what changed. Choose what belongs together. Record that choice. Then give the history useful names.

03 · Read before changing

One file can have several states.

Untracked
A working file has no tracked entry in the index. Git sees a candidate to add, unless an ignore rule hides it.
Tracked
A path belongs to the index or HEAD’s snapshot, including staged additions and deletions. A tracked file can be clean, modified or scheduled for deletion.
Modified
Working-tree content differs from the indexed version. The edit has not necessarily been staged.
Staged
The index differs from HEAD’s snapshot. That difference is selected for the next ordinary commit.
Committed
A version belongs to a recorded commit snapshot. The working copy can already contain newer, uncommitted changes.

git status asks two comparisons.

Compare HEAD to index, then index to working tree; also discover untracked paths. Ordinary status does not create commits, stage content, contact a server or change working files. It may refresh cached index bookkeeping.

git status
git status --short
# First column: index vs HEAD. Second: working tree vs index.
M  index.html    # staged modification
 M styles.css    # unstaged modification
?? notes.txt     # untracked file

MM index.html means you staged one edit, then changed that same file again. Both versions matter. A clean status means the tracked states agree; it does not mean the branch has been pushed. Related: diff, the index, status simulator.

04 · Select content

git add records a version.

“Use this content in the next snapshot.” Git writes or reuses blob objects and updates index entries for selected paths. The working files stay exactly where they are. For ordinary text without conversion rules the staged content matches the bytes you see; configured attributes, clean filters or line-ending normalization can transform stored content.

Working tree<h1>Hello, Git</h1>Still here after add.
Index after addindex.html → blob v2The selected content is now recorded.
HEAD treeindex.html → blob v1Last commit is unchanged.
git add index.html
git add styles.css README.md
git diff --staged
git commit -m "Create landing page"

git add . stages additions, modifications and removals under the current directory; ignored untracked files are normally excluded. From the project root that scope is broad. git add -p selects patch hunks when supported, letting you split independent edits into coherent commits.

New blobs, no new commitNo networkWorking files preserved
Why stage at all? The next commit is a choice, not an automatic photograph of every current edit. You can stage a bug fix while leaving an unfinished design experiment in your working tree. Editing a file after add does not update its staged version automatically.

Common mistake: using add as a permanent “watch this file” instruction. Run it again for new content. Related: diff --staged, restore --staged, commit. add manual.

A diff is a question with two endpoints.

A hunk header @@ -a,b +c,d @@ locates a block: old start line a, old line count b; new start line c, new count d. Here two old lines become three new lines. A leading minus removes a line, plus adds one, and a space preserves context. Counts may omit a value of one.

Diff reads content; it does not change files, refs or history and ordinary local comparisons use no network. Untracked files are not automatically included. git diff main...feature instead compares a merge base to feature, useful for reviewing work since divergence; it has different meaning from two dots. Related: status, show, add -p. diff manual.

06 · Record the choice

The commit comes from the index.

git commit normally opens an editor for a message. git commit -m "Create landing page" supplies that message directly. Git writes tree objects describing the staged snapshot, creates a commit object, and advances the current branch. The new commit points to its parent; it does not mutate the old commit.

BeforeHEAD → main → A
→
AfterHEAD → main → B → A

The first commit has no parent. An ordinary later commit has one; a merge may have multiple. Unstaged edits and untracked files are not included by the ordinary no-pathspec form. The commit stores a root tree ID, parent IDs, author and committer identities and times, and a message; optional headers can add information such as a signature.

History: new commitWorking files normally unchangedNo network

Common mistake: “I saved the file, so commit will include it.” Save changes the working tree. Add updates the index. Commit records the index. Options such as -a or explicit paths change selection behavior; -a still does not include new untracked files.

Amend is replacement, not an edit inside an object.

git add README.md
git commit --amend --no-edit
# Or change only the message when the index matches HEAD:
git commit --amend -m "Create accessible landing page"

Amend creates a replacement tip using the index and normally the old tip’s parents. The branch names the replacement. A changed message alone changes the serialized commit and therefore its ID. Staged changes are included even if your intention was only to fix the message.

Shared-history caution. Amending a published tip makes your branch disagree with people who kept the original ID. Coordinate before replacing shared history. This is not a network operation until you push. Related: rebase, reflog.
07 · Read history and snapshots

Follow parents. Inspect objects.

git log

git log
git log --oneline
git log --graph --decorate --all

Walk reachable commits, usually starting at HEAD. --oneline abbreviates IDs and messages; --graph draws topology; --decorate shows names; --all starts from refs beyond the current branch.

Not a record of every command you ran, and not necessarily every object retained on disk. No history or work changed; no network. Related: reflog, rev-list.

git show

git show HEAD
git show HEAD:index.html
git show v1.0

Inspect an object. For an ordinary commit, show typically displays metadata and a patch against its parent. The colon form reads a path from a snapshot. Annotated tags expose tag metadata as well as the tagged object.

Merge commits have special diff formats; show is not always “the complete contents of every file.” No history or work changed; no network. Related: diff, cat-file.

08 · Names are cheap

A branch is a reference, not a directory.

r : branch_name ↦ commit_IDA conceptual mapping from a branch name to the tip commit it currently names.
HEAD→refs/heads/main→B
git branch                  # list local branches
git branch experiment       # create a ref at HEAD; stay here
git switch experiment       # change the checked-out branch
# Alternative to the previous two commands, if the name is new:
git switch -c experiment

A new branch usually requires little more than another name for the same commit. Nothing copies all the files or objects. An ordinary commit then advances only the checked-out branch. git branch alone is inspection; git branch <name> creates a ref without switching.

git switch changes HEAD and updates the index and working tree for the destination. It generally preserves compatible uncommitted changes or refuses a switch that would overwrite them; a dirty tree is not automatically thrown away. These commands do not need a remote or reconstruct existing commits.

HEAD tells Git where “here” is.

Normally HEAD symbolically names a branch. In a detached HEAD, it directly identifies a commit instead. You may still commit, but no local branch advances to retain those new commits for you.

AttachedHEAD → main → B
⇄
DetachedHEAD → B
git switch --detach HEAD~1
# Explore; if you make work you want to keep:
git switch -c saved-experiment

Why switch instead of checkout? git checkout experiment remains valid. Checkout historically switches branches and restores paths; switch and restore separate those intentions. Checkout is not obsolete. Compare their exact targets in the dedicated table. switch manual · checkout manual.

Part III · Histories interact

Separate lines of work meet.

Before choosing merge, rebase or cherry-pick, look at the ancestry. The commands make different promises about identity and topology.

09 · A graph with a direction

Commits remember their parents.

Let G = (V, E) be the commit graph. V is the set of commit objects. We draw a directed edge from each child to each parent: (C, P) ∈ E. Newer commits often appear on the right, but the arrows point back into ancestry. Horizontal placement is not a timestamp guarantee.

C₃ → C₂ → C₁    and    M → {C, D}
deg+parents(v) = 0, 1, or ≥ 2Zero for a root; one for an ordinary non-root commit; multiple for a merge. These are outgoing parent edges.
Directed
A child names its parents; the parent does not need to be changed to “know” a new child.
Acyclic
Following parent edges in a valid commit history never leads back to the same commit.
Graph
History can branch and merge. It is more expressive than a single chronological list.
Ancestor / descendant
P is a proper ancestor of C if a nonempty path of parent edges leads from C to P. Then C is a descendant of P.

Define Reach(r) as the tip named by ref r plus all commits reachable by following parent edges. git log main explores this set; git rev-list main emits reachable commit IDs. Their options can filter or change the traversal.

git merge-base main experiment
git rev-list --count main
git log --graph --decorate --all --oneline

For tips A and B, common ancestors belong to Reach(A) ∩ Reach(B). A merge base is a best common ancestor: none of the other common ancestors is its descendant. There can be multiple best bases, for example in criss-cross histories; merge strategies may combine them into a virtual base. merge-base manual.

10 · Two meanings of a successful merge

Sometimes a reference can simply advance.

Suppose main names B and feature names D in the linear ancestry D → C → B → A. Every commit reachable from main is already reachable from feature.

Before fast-forwardmain → B
feature → D → C → B
→
Aftermain, feature → D
no new commit
A ∈ Reach(B) ⇒ ref A can fast-forward to BHere A and B denote the current and target tips, including equality. Fast-forward requires ancestry, not merely newer dates.
git switch main
git merge --ff-only feature

--ff-only refuses if histories diverged. A regular git merge feature can fast-forward when allowed by options/configuration; --no-ff can request a merge commit even when advancing a ref would be possible.

A three-way merge uses a shared baseline.

With main at D and feature at C in the graph above, Git compares base B → ours D and base B → theirs C. The base distinguishes changes introduced on each side from content that was already shared. A successful true merge records an integrated tree and a new commit M with both tips as parents.

This updates the current branch, index and working tree. It does not move the other branch or rewrite its commits. A merge uses local objects; “merge” itself does not fetch. Start with a clean or safely saved working tree so unrelated edits do not complicate integration.

Fast-forward: ref updateDiverged merge: new commitNo network

When the same lines disagree

Imagine B said <h1>Hello</h1>. Main changed it to “Welcome”; feature changed it to “Hello, world”. Git cannot infer your intended wording.

<<<<<<< HEAD
<h1>Welcome</h1>
=======
<h1>Hello, world</h1>
>>>>>>> feature

The working tree carries conflict markers. The index may hold separate stage-1 base, stage-2 ours and stage-3 theirs entries instead of one resolved stage-0 entry. Some conflict kinds lack one of those entries. Fix the file, remove the markers and stage the result:

printf '<h1>Welcome to our project</h1>\n' > index.html
git add index.html
git merge --continue
# To abandon an in-progress merge instead:
git merge --abort

The short printf is a one-line demonstration; preserve other real file content when resolving. Abort attempts to reconstruct the pre-merge state, but pre-existing uncommitted changes can make that difficult. Other conflicts include delete/modify and rename conflicts. merge manual.

11 · Same intent, new ancestry

Rebase reconstructs commits.

On feature, git rebase main takes selected changes from feature’s commits and reapplies them on top of main. In this simple diverged example D and E become D′ and E′. Existing objects D and E are not physically moved or edited.

Before · lines connect parents
A──B──C  main
   └──D──E  feature
After
A──B──C  main
      └──D′──E′  feature
D′ ≠ D,   E′ ≠ EChanged parent IDs change serialized commit content. Committer metadata commonly changes too.
git switch feature
git rebase main
# If stopped by a conflict: edit, then
git add index.html
git rebase --continue
# Alternative: cancel the entire in-progress rebase
git rebase --abort

A rebase may skip already-applied changes, drop commits that become empty, or do nothing if already up to date; options influence those cases. The simple diagram describes a nontrivial replay, not a guarantee that every invocation creates new objects. Merge topology also needs special handling such as --rebase-merges.

Why shared history needs coordination. A colleague may have based F on the original E. After you publish E′, their F still points to E. They must reconcile those different ancestries; duplicate-looking commits or repeated conflict resolution can result. Rebase is useful for preparing private work. Rewriting shared refs requires an agreed plan, not just a force-push flag.

Rebase updates the current branch, index and working tree; it uses local history and can stop for conflicts. Save unrelated edits first. Related: merge, amend, reflog. rebase manual.

12 · Bring one change across

Cherry-pick transfers a change, not ancestry.

Before: feature  A──B──X
        main     A──B──C

After:  feature  A──B──X
        main     A──B──C──X′
git switch main
git cherry-pick <commit-id-of-X>

Git applies the selected commit’s change to the current state, normally recording a new commit X′ with C as parent. Feature still names X. This is useful for applying a specific fix without merging a whole feature branch.

The parent and typically committer metadata differ, so X′ has another identity even when the patch resembles X. Conflicts can require editing, git add and git cherry-pick --continue; --abort cancels the operation. Options such as --no-commit or --ff can change the result. Selecting a merge commit requires choosing a mainline parent.

Normally creates a commitUpdates index + working treeNo network

Common mistake: expecting all prerequisites from the feature branch to come along. Related: merge, rebase, revert.

13 · Two repositories, independent names

Fetch learns. Integration decides. Push proposes.

A remote is a configured name for another repository and its access information. It need not be GitHub or even a different computer.

git remote
git remote -v
git remote add origin https://github.com/USER/git-demo.git

The first two commands inspect configuration; adding origin changes local config. None of these commands uploads your history. The example URL is a placeholder and requires a repository and appropriate access to be usable.

main

Your local branch: refs/heads/main. It advances as you commit or integrate work.

origin/main

A local remote-tracking ref: refs/remotes/origin/main. Usually your last learned position of origin’s main, updated by fetch and sometimes a successful push.

Fetch: obtain objects and update tracking information.

git fetch origin
git log --oneline main..origin/main
git diff main origin/main
Before fetchmain → B
origin/main → B
→
After remote gains Cmain → B
origin/main → C → B

With the usual clone refspec, fetch downloads needed objects, updates remote-tracking refs and records fetched tips in FETCH_HEAD. It does not automatically integrate origin/main into the checked-out main or change your working files. Refspecs control which refs are fetched and updated; tags may be fetched too. fetch manual.

Pull: fetch followed by an integration policy.

git pull --ff-only origin main   # refuse divergent history
# Alternative policies, not commands to run consecutively:
git pull --no-rebase origin main # merge policy
git pull --rebase origin main    # rebase policy

Pull fetches, then tries to integrate the selected history into the current branch. Options and configuration determine whether it fast-forwards, merges, rebases, or refuses divergence. Specify the policy you intend; do not assume an unconfigured plain pull behaves identically across installations. Unlike fetch, integration can change index, working tree and branch history. pull manual.

Push: send objects and request a ref update.

git push -u origin main

Git sends objects the receiving repository needs and asks it to update its main ref. -u records upstream tracking configuration for a successfully pushed or up-to-date local branch, making later defaults and ahead/behind reports useful. Push does not publish uncommitted working files; it publishes reachable committed objects.

RemoteC → B → A
≠
Local proposalD → B → A

If the remote is already at C and your proposed tip D does not descend from C, replacing its main would remove C from that branch’s ancestry. A normal non-fast-forward push is rejected. Fetch, inspect and integrate deliberately. Authentication, permissions, server hooks or branch protections can also reject pushes.

Force is a request to replace shared history. git push --force bypasses the normal ancestry check and may displace others’ work. git push --force-with-lease adds a check that the remote ref still has the expected value. The shorthand often relies on local remote-tracking information, which background fetches can update; an explicit --force-with-lease=refs/heads/main:<expected-id> pins the expectation. A matching lease still does not make a coordinated rewrite unnecessary. push manual.

14 · Give a release a stable name

Tags mark a chosen object.

Lightweight tag

refs/tags/v1.0 → commit

A ref points directly to an object, usually a commit. It has no separate tag message or tagger metadata.

git tag v1.0

Annotated tag

refs/tags/v1.0 → tag object → commit

A tag object stores target, tagger, time and message; it can carry a signature. The target can be another Git object type too.

git tag -a v1.0 -m "First release"
git tag                   # list tags
git show v1.0
git push origin v1.0      # publish this tag explicitly

Use one creation form for the same tag name, not both. A branch advances through ordinary commits; a tag normally stays attached to the chosen object. Tags can be deliberately moved or deleted, so “stable” describes release practice, not an immutable ref type. Creating a tag does not switch branches or change files; pushing a branch alone does not generally publish all tags. Related: show, push, rev-parse.

Part IV · Undo & recovery

“Undo” is not one operation.

Restore content, reposition a reference, or record an inverse change. Those choices affect different parts of the system.

15 · Three very different meanings

Restore. Reset. Revert.

Content

restore

Copy selected content from the index or a tree into the working tree and/or index.

No branch movement.

Position + optional content

reset

Commit form: reposition the current branch/HEAD, optionally resetting index and working files.

Path form only updates the index.

New history

revert

Apply the inverse of a selected change and record it in a new commit.

Keep existing ancestry.

Restore: be explicit about source and destination.

git restore --staged index.html
# HEAD → index. Unstage; keep the working file.

git restore index.html
# Index → working tree. Discard unstaged edits to this path.

git restore --source=HEAD~1 --worktree index.html
# Chosen commit's tree → working file; branch and index stay.
Working-tree restore can discard unsaved-to-Git work. Inspect git diff -- index.html first and preserve edits you might need. Reflog records reference movements; it does not promise recovery of arbitrary overwritten working-tree bytes. --staged alone preserves working files, but replaces their staged selection. restore manual.

For git reset <mode> <commit>, this table assumes a normal attached HEAD and a completed operation. HEAD remains symbolic and the current branch moves to the target. In detached state HEAD itself moves. “Target tree” means the snapshot of that commit.

Reset does not edit or instantly erase the old commit objects. It changes what the branch reaches. Soft reset does not guarantee “everything staged”: if index and working tree already differed, that distinction remains.

Destructive demonstration—not a recovery shortcut. git reset --hard HEAD~2 moves back two first-parent steps and discards tracked index/working-tree changes. It can also delete untracked files or directories in the way of writing tracked paths. It is not equivalent to deleting every untracked file. Save work and verify the target before any hard reset; the recovery section uses a safer rescue branch. reset manual.

Revert: keep the story, add a correction.

Chronological drawing; parent links run right to left:
A──B──C  main
       └──R  main after reverting B
R records an inverse change; B remains an ancestor.
git revert <commit-id-of-B>

Git applies an inverse of B’s change to the current content and normally commits the result. Later edits may cause conflicts; reverting B does not guarantee the entire tree becomes A again. This preserves ancestry that collaborators already share. Reverting a merge requires a mainline choice and has consequences for later merges.

Related: reflog to investigate movement, stash to save work, diff to inspect first. revert manual.

Use -- to separate revisions/options from path arguments where supported. Restore is normally no-overlay: a tracked path absent from the source can be removed to match that source. Checkout’s default overlay differs, which is one reason “they do the same thing” is too broad.

17 · Put unfinished work aside

Stash creates recoverable objects.

git stash is the usual shorthand for git stash push. It saves tracked working-tree and index changes, then normally resets those tracked states toward HEAD so you can do something else. Untracked files need -u; including ignored files needs -a.

refs/stash → W · working-state commit
  • parent 1 → Hcommit that was HEAD
  • parent 2 → Iindex-state commit, itself based on H
  • optional parent → Usaved untracked / ignored files when requested
git stash push -u -m "WIP landing page"
git stash list
git stash apply 'stash@{0}'  # apply, retain the stash entry
# Alternative to apply:
git stash pop               # apply; drop if successful
# When deliberately finished with an entry:
git stash drop 'stash@{0}'

Stashes are special commits referenced through a ref and reflog, not a magical separate drawer. Apply may conflict. Pop keeps an entry when application fails with conflicts. Use apply --index when you also want to attempt restoring the original staged state; plain apply does not promise that distinction.

Drop only after checking your work. Dropping removes a stash entry’s normal recovery handle, not necessarily its objects immediately. Stash is local and not a replacement for a backed-up commit. A default stash also leaves untracked files out, which can surprise you during a branch switch.
18 · History of names

The commit disappeared from the branch.
It may still exist.

Commit history

Follow parent links from named tips. git log asks: which commits are ancestors of this position?

Reflog history

Read local records of ref updates. git reflog asks: where did HEAD or another logged ref point recently?

Before accidental reset: HEAD → main → C → B → A
After:                   HEAD → main ─────────→ A

HEAD reflog, illustrative:
a1b2c3d HEAD@{0}: reset: moving to HEAD~2
c4d5e6f HEAD@{1}: commit: Add navigation
b7c8d9e HEAD@{2}: commit: Add styles

C may be absent from main’s ordinary log but still present in the object store and protected by a reflog entry. Start by inspecting, then create a name before moving anything else.

git reflog
# Identify and inspect the entry; do not assume @{1} is correct.
git show 'HEAD@{1}'
git branch rescue 'HEAD@{1}'
git log --oneline rescue

The branch creation retains the recovered tip without changing the current branch, index or files. Later, switch or integrate only after deciding what to keep. If you intentionally reset the current branch to the recovered ID, a --hard reset would also overwrite local tracked work; recovery of commits and preservation of current edits are separate tasks.

Local, finite memory. Reflogs are not transferred as shared project history by clone/push. Logging depends on repository/ref configuration. Default expiration settings commonly distinguish 90-day entries and 30-day unreachable entries; these are configurable maintenance policies, not a guarantee that a particular object survives that long. Once retention roots and grace periods no longer protect an unreachable object, pruning may remove it. reflog manual.

Common mistake: treating reflog as a backup of every keystroke. It can locate commits after ref movement; it cannot reliably recover content that was never stored as an object. Reflog entries also change position as new operations occur, so inspect before using their numeric selectors.

Part V · Inside Git

Objects first. Names second.

The snapshots have a concrete representation. Understanding that representation explains staging, cheap branching, new commit identities and eventual garbage collection.

19 · The mysterious Git index

A proposed snapshot, with bookkeeping.

The index is a data structure, normally stored in .git/index, mapping paths to modes and object IDs plus stat/cache information. It is not just a list of “files waiting to be committed”. For normal resolved entries it represents a full next snapshot, including unchanged tracked paths; conflict entries are an important exception.

HEAD treeindex.html → v1 styles.css → s1Last committed snapshot.
Indexindex.html → v2 styles.css → s1One selected change, one reused blob.
Working treeindex.html = v3 styles.css = s1You edited the staged file again.
diff --staged : v1 → v2
diff : v2 → v3
diff HEAD : v1 → v3For index.html in this example; status --short reports MM.

An ordinary commit here captures v2, not v3. That is precisely why staging is useful: it decouples the state you are still exploring from the state you choose to record. For conflict inspection, git ls-files --stage shows index stages and object IDs.

20 · Four principal object types

A snapshot is a web of reusable objects.

Blob
Stores content bytes. It does not intrinsically store a filename or parent directory. Identical stored content under different names can share one blob.
Tree
Stores entries associating names and file modes with object IDs: blobs, subtrees and special entries such as submodule gitlinks. A root tree describes the snapshot’s hierarchy.
Commit
Names a root tree and zero or more parent commits, and stores author/committer metadata and a message. It ties a snapshot to a position in history.
Annotated tag
Names a target object and type, and stores tag metadata and a message, optionally a signature. A lightweight tag has no separate tag object.

A commit therefore represents a snapshot logically, even if object reuse and packed deltas make physical storage much smaller than independent directory copies. Git can compute a diff between two snapshots; that does not make the commit itself merely a saved patch.

21 · Content addressing

An object’s content determines its name.

OID = H(header ∥ content)
blob OID = H(“blob ” ∥ decimal(n) ∥ NUL ∥ content)∥ means byte concatenation. n is the byte length of the stored content; NUL is one zero byte. H is the repository’s object hash function.

The object header contains its type and size. Git does not simply use a hash of raw file bytes as the blob ID. Loose-object compression happens around that representation; recompressing or repacking does not rename the object.

printf 'hello\n' | git hash-object --stdin
# SHA-1 repository, six content bytes:
ce013625030ba8dba906f756967f9e9ca394464a

Git historically uses SHA-1 (40 hexadecimal digits) and also supports SHA-256 repositories (64 digits). git rev-parse --show-object-format reports the storage format; git init --object-format=sha256 selects SHA-256 for a new repository on supporting Git versions. Transport/tool compatibility across object formats depends on the installed Git and host; do not assume every server accepts every format.

Within a given format, identical blob content produces the same object ID, enabling reuse. Hashes also let Git detect mismatched object content. That is not a complete trust or security model: identity verification, signatures, access controls, transport security, collision handling and implementation behavior are separate concerns. Git’s hash transition design.

22 · Identity propagates upward

A Merkle-DAG-like structure

Objects contain the IDs of objects they reference. Editing src/app.js changes its blob ID; a tree entry then changes, giving the src tree a new ID. Its parent root tree also changes, and a commit that points to the new root has a different ID. Unchanged sibling blobs and trees can still be reused.

Identical files do not imply identical commits.

commit X
 tree T
 parent B
 author Ada …
 committer Ada …
 message: Fix navigation
commit Y
 tree T
 parent C
 author Ada …
 committer Ada …
 message: Fix navigation

These commits name the same root tree T but different parents. Their serialized content and IDs differ. Timestamps, messages, identities or optional headers can likewise change an ID. Rebase and cherry-pick alter commit context even when the visible patch looks familiar.

24 · Physical storage

A tour of .git/

.git/                      # common layout, not a universal literal listing
├── HEAD                   # symbolic ref, or detached commit ID
├── config                 # repository-specific configuration
├── index                  # staging representation; created when needed
├── objects/
│   ├── ab/cdef…           # loose compressed object, if present
│   └── pack/              # packs and indexes
├── refs/
│   ├── heads/             # local branch refs
│   ├── remotes/           # remote-tracking refs
│   └── tags/              # tag refs
├── logs/                  # reflogs, when enabled/present
└── packed-refs            # packed refs in the files ref backend

This is a conceptual tour, not a promise that every item exists immediately after init. Refs can be packed rather than remaining individual text files; other ref storage backends can differ. Objects can live in packs. Linked worktrees may have a .git file pointing elsewhere, with some metadata shared and some per worktree. A bare repository has no normal checked-out working tree.

Use git rev-parse --git-dir, git show-ref and other Git commands to inspect the repository rather than assuming a fixed filesystem layout or editing ref files by hand. Repository layout manual.

25 · Reuse, pack, retain, collect

Snapshot semantics; economical storage.

Loose objects

Objects may first exist as separate compressed files. Many snapshots reuse existing blobs and trees instead of duplicating them.

Packfiles

Packs store many objects together. Some entries use deltas against other objects to reduce size. Pack indexes help locate object IDs.

Reachability

Refs, reflogs and other retention roots keep objects relevant. Unreachable objects can remain for a while before maintenance prunes them.

git count-objects -v
# Housekeeping when appropriate, not needed after every commit:
git gc

count-objects -v reports storage counts and sizes without changing history. Garbage collection can repack objects, maintain indexes, expire reflogs and prune eligible unreachable objects according to settings. It normally preserves reachable history; it changes storage and can remove recovery opportunities.

Deleting a branch removes a name, not a whole independent folder of commits. Objects still reachable through another branch, tag or retained reflog may survive. Even unreachable objects are not necessarily deleted immediately. Conversely, retaining an object physically does not make it appear in git log main.

During recovery, preserve evidence first. Avoid aggressive pruning or manual object deletion. Default maintenance has safeguards and grace periods; --prune=now removes an important time cushion and can be unsafe with concurrent writers. A pack delta is a storage optimization, not the logical parent relationship of a commit. gc manual.

29 · A miniature branch graph

Create names, create commits, connect parents.

HEAD → main → B → A
Create feature at B, commit on main, switch, commit again.
Then merge to connect the two diverged histories.

Conceptual model: commits have parent links; branches name tips. A reset leaves old nodes visible as retained objects.

Scope: two branches, at most ten nodes, no file contents or merge conflicts. An ancestor merge fast-forwards; a diverged merge makes a two-parent commit. A tip reset models ref movement only, like soft reset, without modeling index/files. Newer nodes point to parents; faded nodes are unreachable from the two branch tips, not automatically deleted.

30 · Keep noise out

Ignore rules are for untracked candidates.

# .gitignore
*.log
.env
node_modules/
build/

Untracked → ignored

Matching files are normally omitted from status and broad add operations.

Tracked → still tracked

An ignore rule does not remove an existing index entry or erase old commits.

Patterns are interpreted relative to the ignore file’s location, with slash rules, directory suffixes and negation available. Ignore rules are not a secret-management boundary. Already committed secrets remain in history even after removing the current file.

# To stop tracking a file while retaining your working copy:
git rm --cached debug.log
git add .gitignore
git diff --staged

This stages removal from the next snapshot; it does not rewrite earlier snapshots. A future checkout or collaborator may experience that removal through history. Related: status, add, rm. gitignore manual.

31 · A few more useful instruments

Small commands with distinct jobs

git rm / git mv

git rm old.html
git mv draft.html index.html

Rm removes a tracked path from working tree and index, staging deletion; --cached removes only from the index. Mv renames a path and updates the index. Neither creates a commit.

Git’s snapshots do not need a permanent “rename object”; later comparisons infer renames from content similarity. Check local edits before removal; ordinary rm has safeguards, while force can override them.

git clean

git clean -nd  # preview untracked files/directories
# Only after inspecting that exact preview:
git clean -fd

Deletes untracked files; -d includes directories. Ignored files are normally spared unless options such as -x are used.

Destructive. No commit or reflog entry saves those deleted bytes. Preview, then copy anything worth keeping elsewhere.

git blame / git grep

git blame -L 1,20 index.html
git grep -n 'navigation'

Blame attributes lines to commits under its tracking rules; it helps locate context, not judge who caused a bug. Grep searches tracked content by default and can search specified trees. Both are inspection commands.

git bisect

git bisect start
git bisect bad
git bisect good <known-good-id>
# Test each selected checkout; mark good or bad.
git bisect reset

Git chooses candidate commits to narrow where a regression appeared. It checks out revisions; save work first. On a simple linear search interval, binary-style elimination needs about log₂(N) decisions; DAG topology, untestable commits and inconsistent tests complicate this.

git worktree

git worktree add ../git-demo-review -b review
git worktree list

Add a second checkout sharing the repository’s objects and most refs. Each worktree has its own HEAD and index. This avoids repeatedly switching one directory; Git normally prevents checking out the same branch twice.

git sparse-checkout

git sparse-checkout init --cone
git sparse-checkout set src docs

In a project with these directories, narrow the populated working tree using sparse rules. The history remains; this is different from a partial clone that omits some objects until needed. Root-level files are included in cone mode.

This changes working-tree population and index behavior, not commit ancestry. Use a clean working tree; related: clone --filter, sparse-checkout disable.

git shortlog -sn summarizes commits by author for the selected history. Like blame, an attribution summary reflects metadata and traversal rules rather than a complete measure of contribution.

33 · Under the porcelain

Build the connection by hand.

User-facing commands such as add and commit are often called porcelain. Lower-level plumbing exposes objects, the index and refs directly. The distinction describes intended use, not a separate repository format.

An isolated Linux exercise: bytes → blob → tree → commit → ref

Run only in a fresh temporary demonstration repository. The shell variables are local to this exercise. The supplied identity is fictional demonstration metadata.

demo_dir=$(mktemp -d /tmp/git-object-demo.XXXXXX)
cd "$demo_dir"
git init -b main
git config user.name "Demo Author"
git config user.email "demo@example.invalid"
printf 'hello\n' > hello.txt

blob_id=$(git hash-object -w hello.txt)
git cat-file -t "$blob_id"    # blob
git cat-file -p "$blob_id"    # hello

git add hello.txt
tree_id=$(git write-tree)
git ls-tree "$tree_id"
commit_id=$(printf 'Built from objects\n' | git commit-tree "$tree_id")
git cat-file -p "$commit_id"
git update-ref refs/heads/main "$commit_id"
git rev-parse HEAD
git show-ref
git rev-list main

hash-object computes an ID; -w also stores the object. cat-file reveals its type or content. write-tree writes a tree from the current resolved index. commit-tree creates a commit without advancing a branch; omitting -p makes this a root. update-ref safely updates a ref through Git’s machinery. HEAD already symbolically named main, so it now resolves to that commit.

No working files move when a blob is written. No branch moves when commit-tree merely returns an ID. A stored object and a name that makes it reachable are separate things.

Plumbing can bypass porcelain safeguards. update-ref can reposition history without updating the index or working files. Do not use this exercise against the website repository. In scripts that update an existing ref, supplying the expected old ID to update-ref can protect against a concurrent change.
Read-only object inspection in an existing repository
git rev-parse HEAD
git cat-file -p HEAD
git cat-file -t HEAD^{tree}
git ls-tree HEAD
git show-ref
git rev-list --parents --max-count=5 HEAD
git count-objects -v

These forms inspect available objects and refs. They do not create commits or overwrite files. In partial clones, some object-reading operations may fetch missing objects on demand; the guide’s “no network” labels assume a normal local repository with the required objects present.

34 · Clear away the misleading shorthand

Git ideas that are easy to misunderstand

“Add moves a file into staging.”

The working file stays. Git records selected content and updates the index.

“A commit stores only a diff.”

A commit names a snapshot tree. Deltas may optimize storage; diffs are computed comparisons.

“A branch has its own project copy.”

A branch is fundamentally a ref into shared object history. A checkout is separate.

“GitHub is Git.”

Git works locally. Hosting and collaboration are additional services.

“Pull and fetch are synonyms.”

Fetch learns remote state. Pull also attempts integration into the current branch.

“Reset means undo.”

Which form, target and mode? Ref movement and content replacement are distinct.

“Delete a branch, delete its commits.”

Other refs or retention roots may keep those commits; deletion is not immediate object erasure.

“A message edit only changes the message.”

Amending changes the serialized commit and therefore its identity, with consequences for descendants.
