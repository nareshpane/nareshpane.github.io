# 6. Create the route geometry correctly

Create:

03_build_routes.py

The purpose is to transform GTFS shapes.txt point sequences into GIS LineString geometries.

Use the relationships:

routes.txt
    route_id
       ↓
trips.txt
    route_id
    shape_id
    direction_id
       ↓
shapes.txt
    shape_id
    shape_pt_lat
    shape_pt_lon
    shape_pt_sequence

Important:

A GTFS route is not necessarily represented by one shape.

One route_id may have:

* two directions
* short turns
* branches
* alternate terminals
* different service patterns
* multiple distinct shape_id values

Do not collapse all shapes belonging to a route into one arbitrary LineString.

# 7. Build a complete route-pattern dataset

For each unique GTFS shape:

1. filter the rows belonging to a shape_id
2. sort by shape_pt_sequence
3. validate the sequence
4. create an ordered sequence of longitude/latitude coordinates
5. create a Shapely LineString
6. associate the shape with its route metadata through trips.txt
7. associate the route with metadata from routes.txt

Save a detailed GeoJSON:

data/processed/transit_route_patterns.geojson

Use:

EPSG:4326 / WGS 84

The GeoJSON should retain useful attributes where available, including:

* route_id
* route_short_name
* route_long_name
* route_type
* route_color
* route_text_color
* shape_id
* direction_id
* count of trips using that route/shape combination
* geometry

If one shape_id is associated with multiple trip records, do not unnecessarily duplicate identical geometry hundreds of times. Reduce it to meaningful unique route/shape/direction combinations and include a trip count.

If the actual feed structure requires a slightly different treatment, inspect the data and implement the most logically correct representation. Explain the decision in the documentation rather than forcing the data into an incorrect assumption.
